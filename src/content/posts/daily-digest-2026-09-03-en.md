### Decoding the new AI lingo: Loops, harnesses, squads, hill climbing… oh my!

GitHub Senior Director of Developer Advocacy Cassidy Williams breaks down a set of AI-agent terms that surfaced on the GitHub Podcast with host Marlene Mhangami. "Loop engineering" means designing a repeatable system around an agent instead of one-off prompting, for example a scheduled loop that fetches issues, hands them to an agent, validates the output, and escalates anything that gets stuck. One implementation, called "Ralph Loops," has an agent work through a detailed task iteratively until it is done, though the piece notes this can get expensive because of token consumption. "Squads" describes a group of agents split into roles such as planning, vetting, implementing, testing, and reviewing, while "fleets" refers to multiple agents running in parallel on separate tasks. "Harness" is defined as everything surrounding a model, including tools, permissions, memory, context, and orchestration, with GitHub Copilot cited as an example. "Hill climbing" is the practice of improving an agent over time through evaluations and feedback, and the piece also distinguishes "closed models" (API-only access), "open weights" (weights available but not necessarily the data or methods), and "open source models" (weights, code, data, and training process all public). It also introduces the "forward deployed engineer," a customer-facing technical role focused on helping teams integrate AI tools into their existing systems.

> 💡 **Why it matters**: Having precise shared vocabulary for loops, harnesses, and squads reduces miscommunication when teams design or compare agent orchestration architectures.

### [Building Reproducible AI Evaluation Workflows with Docker Sandboxes](https://www.docker.com/blog/building-reproducible-ai-evaluation-workflows-with-docker-sandboxes/)

_Docker_

Docker, in a post by Docker Captain Karan Verma published September 2, 2026, describes how to use Docker Sandboxes to make AI evaluation workflows reproducible. The core idea is an executor abstraction: an evaluation definition can run either `local`, directly on the host, or `sbx`, delegated to Docker Sandboxes, selectable through configuration alone, keeping the evaluation logic independent of the execution environment. Each run captures a structured artifact recording the chosen executor, the exact command, stdout, stderr, the exit code, and execution time in milliseconds, so a run can later be reproduced and checked. Evaluation definitions are written in YAML, and switching environments is as simple as changing a block such as `execution.executor: sbx`. An open-source "SBX AI Evaluation Kit" can be applied with the command `sbx run claude --kit .`, and it generates a configuration digest that deterministically links a given config to its artifacts. Running an evaluation suite that groups multiple definitions together also produces an aggregated summary across the whole run. Related documentation is available at `docs.docker.com/ai/sandboxes/`.

> 💡 Capturing structured evidence down to exit code and duration turns AI agent evaluation into something as reproducible as CI, making it possible to tell whether a benchmark score shift came from a model change or an environment difference.

### [Below the Harness: Governing a Multi-Model, Multi-Harness World](https://www.docker.com/blog/below-the-harness-governing-a-multi-model-multi-harness-world/)

_Docker_

> 💡 Controlling process execution, credentials, and network access at a layer outside the execution loop, rather than through prompt-level instructions, is what lets an organization keep consistent audit logging and spend control regardless of which model or harness is in use.

### [Metal3 meets KubeVirtBMC: Provisioning KubeVirt VMs like bare metal](https://www.cncf.io/blog/2026/09/02/metal3-meets-kubevirtbmc-provisioning-kubevirt-vms-like-bare-metal/)

_CNCF_

Metal3, a CNCF Incubating project, brings bare-metal host management into the Kubernetes ecosystem by using OpenStack Ironic internally and abstracting hosts through a BareMetalHost custom resource. KubeVirtBMC gives KubeVirt virtual machines virtual BMC endpoints so they can be managed through the same interfaces used for real bare-metal provisioning. Communication runs mainly over Redfish, with KubeVirtBMC exposing an endpoint like `/redfish/v1/Systems/1`, and the `redfish-virtualmedia` driver boots provisioning images by attaching an ISO instead of using PXE. A BareMetalHost resource needs a `bootMACAddress` matching the actual VM interface's MAC address, pinned in the demo to `02:00:00:00:00:01`. The BMC address must use the `redfish-virtualmedia+http://...` format to explicitly request plain HTTP, since omitting the `+http` suffix defaults to HTTPS and causes the connection to fail. When Metal3 tells Ironic to power on a host or attach a boot image, Ironic sends Redfish requests to KubeVirtBMC, which translates them into Kubernetes API calls that control the underlying KubeVirt VM. Hosts move through the lifecycle states registering, inspecting, preparing, available, provisioning, and provisioned, and the setup requires cert-manager along with the Ironic Standalone Operator and Bare Metal Operator deployments.

> 💡 Reproducing the bare-metal provisioning flow through a virtual BMC lets a team validate Metal3-based provisioning procedures without real hardware, which operations teams can use to test automation before production gear is available.

### [Kubernetes v1.37: etcd RangeStream Cuts Memory Use on Large List Reads](https://kubernetes.io/blog/2026/09/01/kubernetes-v1-37-etcd-range-stream/)

_Kubernetes_

etcd RangeStream graduates to beta in Kubernetes v1.37; it's a streaming version of etcd's existing unary `Range` RPC that takes the same `RangeRequest` and returns the same result set, but splits the response into chunks instead of assembling it all at once. The old unary Range assembles a full page before sending it, so the same payload sits in memory on both etcd and the API server at the same time while it's being decoded, and because page size is bounded by key count rather than object size, memory usage was hard to predict. RangeStream tunes its chunk size adaptively to the size of the values being returned, bounds collections of large objects by bytes rather than key count, and frees memory as the stream progresses. The goal of this approach is to lower peak memory usage on both etcd and the API server when reading large resource lists. The feature requires etcd v3.7 or later and is used in watch-cache initialization and in the fallback path for list requests that can't be served from the cache.

> 💡 Streaming large list reads can reduce the risk of API-server and etcd memory spikes causing OOM kills in big clusters, so operators managing many large resources may want to upgrade etcd to v3.7 or later and test this beta feature early.

### [Automate proxy injection for Amazon EKS on AWS Fargate using Kyverno](https://aws.amazon.com/blogs/containers/automate-proxy-injection-for-amazon-eks-on-aws-fargate-using-kyverno/)

_AWS Containers_

This post describes using a Kyverno `MutatingPolicy` to inject three environment variables, `HTTPS_PROXY`, `HTTP_PROXY`, and `NO_PROXY`, into every container and init container at the moment an Amazon EKS on AWS Fargate pod is admitted. Because the injection happens at admission, before the object is persisted to the API server, it avoids a race condition where a container could make network calls before the proxy configuration is applied. The policy targets pods through a namespace label selector and only affects namespaces labeled `proxy-injection: enabled`, making it opt-in and safe to use in clusters with a mix of Fargate and EC2 nodes. It sets `failurePolicy: Ignore` so pod scheduling isn't blocked if the webhook is unavailable, and the policy applies only to newly created pods, not retroactively to existing resources. The patch is applied using `patchType: ApplyConfiguration` with a Common Expression Language `map()` function that iterates over containers and init containers, with the init-container mutation guarded by `has()` so it only runs when init containers exist. Recommended `NO_PROXY` entries include `localhost`, `127.0.0.1`, `169.254.169.254`, the Kubernetes service CIDR, `.svc`, `.svc.cluster.local`, `.cluster.local`, and `.amazonaws.com` or region-specific AWS endpoints. The policy evaluation happens once per pod at admission and adds no overhead to the pod once it's running.

> 💡 Because the policy evaluates once at admission with no runtime overhead, large Fargate clusters can manage proxy configuration consistently through a single namespace-scoped policy instead of hardcoding it into every deployment manifest.

### [Fast model loading for AI inference on Amazon EKS](https://aws.amazon.com/blogs/containers/fast-model-loading-for-ai-inference-on-amazon-eks/)

_AWS Containers_

AWS describes two configuration-only changes that substantially cut cold-start time for loading AI inference models on Amazon EKS. The first sets Run:ai Model Streamer's S3 chunk size to 4 GiB to match the shard size and tunes timeout and retry settings aggressively for slow S3 requests, cutting weights-loading time for a 64 GiB model, Qwen3-35B, from about 29 seconds to about 12 seconds. The second points PyTorch's compilation artifact cache at NVMe-backed hostPath volumes instead of ephemeral pod storage, letting the cache be reused across pod restarts on the same node. For the 64 GiB model, weights loading accounted for 35% of startup time, about 29 seconds, and torch.compile accounted for 65%, about 53 seconds; for a 203 GiB model, Llama-4-Scout, weights loading was 92%, about 423 seconds, and torch.compile was 8%, about 34 seconds. On a p5.48xlarge instance, applying both optimizations on the same node cut the 64 GiB model's initial launch time from 82 seconds to 16 seconds, an 80% reduction. On the same instance type, the 203 GiB model's launch time dropped from 457 seconds to 32 seconds, a 93% reduction.

> 💡 Both optimizations pay off most when a pod restarts on the same node, so clusters using autoscaling policies that break node affinity or local NVMe cache locality should expect smaller real-world gains than these headline numbers suggest.

### [Kubernetes v1.37: Storage Version Migration Enabled by Default](https://kubernetes.io/blog/2026/08/31/kubernetes-v1-37-storage-version-migration-ga/)

_Kubernetes_

In Kubernetes v1.37, Storage Version Migration, built on the `storagemigration.k8s.io/v1` API, graduates to general availability and is enabled by default in every v1.37 cluster. SVM is a control-plane controller that automatically rewrites resources still stored in an old schema version into the newly designated storage version. This solves the problem of not being able to safely drop an old API version, like `v1alpha1`, because resources still exist in that legacy storage format. It also addresses an encryption-at-rest issue in which existing resources remained encrypted under old keys, or unencrypted, until actively rewritten through the API server. Previously, administrators had to rely on manual `kubectl get`/`kubectl replace` scripts or an external `kube-storage-version-migrator` component, a tedious and error-prone process that SVM now replaces.

> 💡 Cluster operators upgrading to v1.37 should confirm SVM is running by default and verify the automatic migration has completed before proceeding with tasks like rotating encryption-at-rest keys or removing old API versions.

### [Defending the battlefield: Stateful detections for an agentic threat landscape](https://webflow.sysdig.com/blog/defending-the-battlefield-stateful-detections-for-an-agentic-threat-landscape)

_Sysdig_

Sysdig distinguishes stateless detection, which flags individual events in isolation, from stateful detection, which correlates several actions together to reconstruct what an attacker actually did. For example, a terminal shell opening inside a container can be legitimate on its own, but when it's followed by a package manager installation in the same session, that sequence signals compromise. Technically, this is implemented through Observations representing stateful evaluations inside Falco rules, observation link fields that define relationships such as matching process IDs, and correlation operators, `obs.occurs` and `obs.link`, that combine observations into a single rule. Sysdig says 70% of organizations it surveyed use stateful detections, with 91% of adopters deploying them across their cloud environments, resulting in reduced alert noise and faster investigations. Real-world threat examples cited include React2Shell exploits deployed within hours of vulnerability disclosure, AI-assisted intrusions achieving admin access in 8 minutes, credential theft happening within 3 minutes, and JADEPUFFER, autonomous ransomware that targets AI models. Sysdig also offers Falco Feeds by Sysdig, a continuously updated, expert-written set of detection rules for open-source users.

> 💡 Basing detection rules on the sequence of actions rather than single events can catch fast, multi-step intrusions like an AI-assisted attack that gains admin access in 8 minutes, where each individual step looks normal, giving fewer false positives and a higher true-positive rate than stateless rules.

### [BenchMIRT: What are LLM benchmarks actually measuring?](https://huggingface.co/blog/allenai/benchmirt)

_Hugging Face_

BenchMIRT, introduced by AllenAI, applies Multidimensional Item Response Theory from psychometrics to LLM benchmarks, auditing at the level of individual prompts what a benchmark actually measures. It is trained on 100 LLMs across 16 benchmarks covering more than 34,000 questions, estimating both a model's underlying capability and each question's difficulty and discrimination. Without any predefined labels, BenchMIRT independently recovered two dominant dimensions, safety and general reasoning, and this result replicated across multiple analyses. Specifically, BBQ, which covers social bias, aligned more strongly with general reasoning than with safety; WMDP, covering dual-use knowledge, correlated positively with reasoning and negatively with safety; and HarmBench showed mixed signals, with standard and contextual questions tracking safety while copyright questions tracked reasoning. Reasoning benchmarks such as MMLU-Pro, GPQA, MATH, and BBH confirmed alignment with the reasoning dimension as expected. Keeping just 10% of a benchmark's questions generally preserved model rankings, predicting held-out question performance with 79% accuracy versus a 70% baseline, and a 50% reduction in questions often matched the capability measurement of the full benchmark.

> 💡 Because safety and general reasoning turn out to be separate dimensions, a model scoring well on reasoning cannot be assumed to also score well on safety, so safety benchmarks need to be evaluated separately from reasoning benchmarks before deployment.

### [Mapping global methane emissions from space with deep learning](https://research.google/blog/mapping-global-methane-emissions-from-space-with-deep-learning/)

_Google Research_

Google Research and NASA's Jet Propulsion Laboratory present a deep learning system for detecting methane emissions using hyperspectral data from NASA's EMIT instrument aboard the International Space Station. EMIT has an 80-kilometer field of view, 60-meter spatial resolution, and 7.4-nanometer spectral sampling, capturing hundreds of distinct spectral bands per pixel. The detection model is built on a Swin-S vision transformer that analyzes how gas disperses across the surrounding landscape rather than pixel by pixel, simultaneously handling three tasks: plume concentration quantification, plume delineation, and source localization. Against expert-annotated plumes, the model achieves a detection recall of 84%, and across roughly 1,100 EMIT granules it identified about 50% more plausible plumes than before. It successfully mapped plumes at 24 of the world's top 25 methane-emitting landfills. Deliverables include a global plume database on Google Earth Engine, a trained model and synthetic dataset published on Kaggle, and an inference library on GitHub.

> 💡 An 84% recall rate and 50% more detected plumes come from a model trained on synthetic data, so using these results for regulatory or emissions-credit decisions would first require cross-validation against ground-truth sensor measurements.

### [Critical remote code execution in vm2, a widely used Node.js sandbox library](https://about.gitlab.com/blog/critical-remote-code-execution-in-vm2/)

_GitLab_

GitLab's Threat Research Group, using its own AI automated tools, found a critical remote code execution vulnerability in vm2, a widely used Node.js sandboxing library, rated CVSS 3.1: 10.0. The root cause sits in the configuration copied straight from vm2's own README Quick Examples, `require: { external: true, root: './' }`, because in a typical npm project the `./` root also contains `node_modules`, which includes vm2's own installed copy. With the `context` option left at its default `'host'`, calling `require('./node_modules/vm2')` passes the path check and loads the real vm2 through Node's actual `require()`, and nesting a new NodeVM configured to allow `child_process` inside that fully-loaded vm2 bypasses the outer sandbox's restrictions entirely, letting an attacker run arbitrary commands. vm2 had two earlier escape bugs in the same family, a `nesting: true` bypass (GHSA-8hg8-63c5-gwmx) and a `require.root` symlink bypass (GHSA-cp6g-6699-wx9c), and neither of those fixes touches this new bug. All versions up to and including vm2 3.11.6 are affected; the maintainer responded quickly, accepting the private report on July 23, 2026, committing a fix by August 18, and publicly releasing version 3.11.7 on August 24. The 3.11.7 patch, however, only blocks requiring vm2's own lib folder and main file: turning on `require.external: true` with no `root` set at all now just prints a warning and still runs, and pointing a broad `root` at any other file that exposes `child_process` still gives full remote code execution on 3.11.7 with no warning at all. vm2 sees roughly 1.25 million downloads a week and 5 million a month on npm with over 4,000 GitHub stars, so the exposure is wide, and GitLab confirmed it does not use vm2 itself while recommending its GitLab Duo Security Analyst Agent to check a codebase for vm2 usage with risky `require.external` settings.

> 💡 Upgrading to the patched version is not enough by itself, so teams using vm2 need to narrow `require.root` to a folder with no path to `node_modules` or anything reaching `child_process` or `fs`, explicitly set `context: 'sandbox'`, and longer term move to container- or separate-process-based isolation instead.
