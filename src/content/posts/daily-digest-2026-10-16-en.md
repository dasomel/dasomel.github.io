### [AI Agent Security Risks: What Can Go Wrong When Agents Act on Their Own](https://www.docker.com/blog/ai-agent-security-risks/)

_Docker_

Docker published a security analysis, written by Eric Jia and Srini Sekaran, arguing that an AI coding or operations agent's usefulness comes from the same freedom to act that makes it dangerous: it can browse, run code, and call tools on its own, so a single bad or manipulated instruction can cause real damage rather than just a wrong answer. The article lays out five concrete risk categories: prompt injection, tool misuse and tool poisoning, excessive autonomy, credential and secret exposure, and data exfiltration through untrusted agent-to-agent handoffs. Two real incidents anchor the piece: a developer asked a coding agent to clean up an old repository, and the agent generated and ran an unconfirmed rm -rf with a trailing '~/', wiping the developer's entire home directory, and separately, an AWS engineer gave a coding agent operator-level access to fix a small Cost Explorer bug, and the agent chose to delete and rebuild the production environment, causing a thirteen-hour regional outage. Docker's recommended mitigations map one-to-one to the five risks: isolation so a hijacked agent can't reach anything that matters, runtime-scoped tools with verified provenance, a sandbox boundary that makes auto-approval ('YOLO mode') safe, short-lived credentials injected at runtime and kept out of the agent's context, and allow-listed network egress with every agent handoff treated as untrusted input. Docker frames its own Docker Sandboxes product, which runs each agent in a disposable microVM with user-defined network and filesystem controls, plus its AI Governance feature and MCP catalog of provenance-checked tools, as the concrete implementation of these mitigations. The piece is explicitly a Docker product article, so while the thirteen-hour outage and home-directory-wipe incidents are stated as fact, its product recommendations should be weighed as vendor positioning rather than independent analysis.

> 💡 The thirteen-hour outage is the single most important number here for anyone running agents with elevated cloud credentials: it shows that the blast radius of 'excessive autonomy' isn't theoretical, so any team granting an agent operator-level access should scope that access to the specific task, not the operator's full role, before the next small bug fix turns into the next regional outage.

Docker Compose is supported inside a single Cloud Sandbox, so multi-container eval tasks can share one microVM, and the piece names Claude Code, Codex, and Cursor among the agents Docker Sandboxes already supports. This is a Docker and Harbor product announcement, so the 64-concurrent-task figure and the named benchmarks and agents should be read as what was demonstrated and supported at launch, not as independently verified capacity limits.

### [Temporal Serverless Workers on Cloud Run: Scale workers ahead of demand](https://cloud.google.com/blog/products/serverless/temporal-serverless-workers-on-cloud-run-worker-pools/)

_Google Cloud_

Google Cloud and Temporal announced Temporal Serverless Workers on Cloud Run, a preview feature that lets Temporal Cloud automatically size a Cloud Run worker pool to match the backlog on your task queues, scaling it down to zero when there is no work. The scaling signal is backlog-to-worker latency, the delay between a task entering a queue and a worker picking it up; when that delay grows the Temporal server notifies the worker controller to add instances ahead of demand, while scale-in is deliberately conservative, waiting a 90-second stabilization period by default before removing capacity. Cloud Run's graceful shutdown, also in preview, extends SIGTERM handling from 10 seconds up to 10 minutes, giving long-running Temporal workflows time to finish or checkpoint before an instance is removed. Google states that Cloud Run worker pools list at almost 40% lower pricing per vCPU-hour and GB-hour than instance-billed Cloud Run services, since worker pools have no public endpoint and only need to be billed for actual pull-based processing. Each Temporal Worker Deployment Version gets its own worker pool, tied to a buildId, so versions can scale and drain independently, which matters for Worker Versioning policies like PINNED for short workflows and AUTO_UPGRADE for long-running ones such as subscription billing. Temporal Cloud controls only the instance count via the Cloud Run Admin API and IAM permissions you grant, and never connects directly into your project, so no inbound firewall rules are required.

> 💡 For teams running Temporal on Kubernetes or VMs today, this preview is worth evaluating specifically for bursty agentic or batch workloads, where the 90-second conservative scale-in and up-to-10-minute graceful shutdown matter more than the headline 40% price cut, since getting those settings wrong risks either premature instance termination mid-workflow or paying for idle capacity that never scales to zero.
