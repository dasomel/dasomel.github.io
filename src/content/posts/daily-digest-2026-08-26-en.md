## 🔥 Top Story

### Shopify’s CEO threatened to ban Claude Code. Anthropic had already closed the feature request.

Shopify CEO Tobi Lütke said on X he's considering banning Claude Code at the company, not because the tool is bad but because Anthropic still won't natively read AGENTS.md. Shopify runs thousands of developers in a single massive monorepo where coding agents pick up instruction files recursively down the directory tree, so every agent needs the right file in every folder. AGENTS.md, introduced by OpenAI in 2025 and now stewarded by the Linux Foundation's Agentic AI Foundation, has become a de facto standard used by over 60,000 projects and tools like Codex, Cursor, Gemini CLI, and GitHub Copilot. Claude Code instead relies solely on its own CLAUDE.md, so a directory missing one of the two files leaves a subset of developers working with what Lütke called a 'lobotomized' agent. Anthropic offers workarounds like importing AGENTS.md into CLAUDE.md or symlinks, but has closed a feature request for native recursive AGENTS.md discovery as 'not planned.' Shopify has built automation to paper over the gap, but Lütke argues platform teams shouldn't have to pay that complexity tax at all. The dispute highlights a real fragmentation risk as more coding agents converge on the same large codebases without a shared convention.

> 💡 **Why it matters**: Any org running multiple coding agents against the same monorepo should treat CLAUDE.md/AGENTS.md drift as a silent correctness risk and automate keeping both files in sync until Anthropic ships native support.

### [The lazy developer’s guide to observing your own code](https://www.cncf.io/blog/2026/08/25/the-lazy-developers-guide-to-observing-your-own-code/)

_CNCF_

This CNCF blog post addresses developers' common resentment toward being asked to 'shift left' on observability by instrumenting application code with OpenTelemetry themselves, and makes the case for why this actually benefits developers, not just SREs. It lists five concrete benefits: instrumentation reduces debugging time, accelerates development and deployment, surfaces slow paths and hidden retries before they hit production, helps developers reason about unpredictable microservices interactions, and helps untangle inconsistent quality from AI-generated ('vibecoded') code. Drawing on developer interviews, the piece identifies real pain points: SDK/SIG maturity varies wildly by language, languages like Rust and Elixir lack zero-code (automatic) instrumentation and require starting from scratch, there are too many competing options (SDKs, eBPF, compile-time instrumentation), and API instability, painful dependency upgrades, and high-cardinality metrics all add friction. Its practical advice is to start with zero-code instrumentation where available (Java, .NET, Python, JavaScript, PHP, Go), fill gaps with manual instrumentation, practice observability-driven development by instrumenting code as it's written rather than retroactively, and use AI carefully to assist with instrumentation work. On what to instrument, it recommends adding spans only to meaningful units of work — inbound requests, outbound calls to databases/caches/APIs/queues, and business-critical operations — rather than instrumenting every method call, which just creates noise (the excerpt available cuts off before further tips).

> 💡 When rolling out instrumentation standards to a new team or language, factor in that manual-instrumentation burden spikes sharply for languages without zero-code auto-instrumentation (Rust, Elixir), meaning observability cost should be weighed as an architectural decision at stack-selection time, not bolted on afterward.

### [Stop trying to learn all of Kubernetes at once](https://www.cncf.io/blog/2026/08/25/stop-trying-to-learn-all-of-kubernetes-at-once/)

_CNCF_

Written by Joep Piscaer of Portainer.io for the CNCF blog, this piece argues that Kubernetes learning resources fail beginners by dumping too much at once, and instead proposes five pieces of mental scaffolding to internalize before diving into configuration details. First is desired state and reconciliation — the single mechanism underlying self-healing, scaling, and rollouts, where you declare what should exist rather than commanding actions and the system continuously reconciles reality against that declaration. Second is the control-plane/worker split and what 'disposable' really means: unlike a sick vSphere ESXi host that gets nursed back to health, a sick Kubernetes node just gets replaced, since any healthy node can run any workload. Third is the four networking layers — container to pod, pod to service, service to ingress, ingress to the outside world — with the insight that most networking confusion is really confusion about which layer a problem is occurring at. Fourth is treating requests and limits as a survival contract rather than a suggestion, since misconfiguring them either wastes capacity or gets pods evicted at the worst possible moment, making this the most common root cause behind 'works in staging, falls over in production.' Fifth is understanding why CNI and CSI exist as plugin interfaces rather than built-in implementations — a deliberate flexibility tradeoff that, once understood, makes the sprawling ecosystem of networking and storage plugins look intentional rather than chaotic. The author concludes that everything else — service mesh, policy engines, GitOps — can wait until a real problem makes the need for it obvious, and points to a free vendor-neutral primer at kubeschool.portainer.io.

> 💡 Platform teams building onboarding material should consider adopting these five scaffolding concepts — especially reframing requests/limits as a survival contract rather than a suggestion, and nodes as disposable rather than assets to nurse — as a minimum curriculum, since misunderstanding them is called out here as the most common root cause of 'works in staging, falls over in production' incidents.

### [Granite 4.2 LLMs: How They're Built](https://huggingface.co/blog/ibm-granite/granite-4-2)

_Hugging Face_

This IBM Granite team post on Hugging Face is a detailed engineering walkthrough of how Granite 4.2 was built. The models use a dense, decoder-only transformer with Grouped Query Attention (40 heads, 8 KV heads), RoPE (θ=10,000,000), SwiGLU MLPs, RMSNorm, and untied input/output embeddings, with all three sizes (3B, 8B, 30B) sharing the same architecture and training recipe. Pre-training ran on roughly 15 trillion tokens across a five-phase schedule that extends context to 512K in the final long-context phase, and SFT drew on about 7.2 million samples (~100B tokens, ~65B trainable) split 31.6% agentic and 68.4% non-agentic, with the agentic corpus dominated by software engineering (69%), tool calling (12.1%), and terminal use (8%) trajectories generated via scaffolds like OpenHands, SWE-agent, Gemini CLI, and Codex. The 30B model gets an extra phase-2 SFT pass focused on agentic coding (retaining 16% replay data), and the 8B/30B models then go through a multi-stage, multi-environment reinforcement learning pipeline that teaches them to act as agents inside real sandboxed environments. Served through an OpenAI-compatible endpoint like vLLM, the models emit tool calls in the standard OpenAI function-calling format, letting them plug into existing agentic harnesses without extra glue code.

### [Quantization-Aware Healing: a compressed, 4-bit model that outperforms its full-precision original](https://huggingface.co/blog/MultiverseComputingCAI/quantization-aware-healing)

_Hugging Face_

Multiverse Computing introduced Quantization-Aware Healing (QAH), a technique for recovering accuracy in a model that has been both structurally compressed (layers, heads, or neurons removed) and quantized to 4 bits, by distilling directly from the original pre-compression, full-precision model as a frozen teacher via KL divergence. This sidesteps the limitations of quantization-aware training (QAT), which re-runs an already expensive multi-stage post-training process through a noisier low-precision forward pass and can become unstable, and quantization-aware distillation (QAD), which distills from the recovered bfloat16 checkpoint and thus caps the quantized model's accuracy at that checkpoint's own ceiling. To make this work at 32K-token context, QAH reuses a memory-efficient chunked KL-divergence loss from a companion paper that computes divergence one sequence slice at a time, avoiding materializing the full vocabulary-by-sequence grid. Applied to a GPT-OSS 120B model structurally compressed to 60B parameters and quantized to MXFP4, QAH beat its own bfloat16 (16-bit) version on 7 of 9 benchmarks, with the largest gains on long-context reasoning (+7.4 on AA-LCR) and math (+5.6 on AIME 2025). Remarkably, the QAH 60B model — at half the parameters and roughly a quarter of the weight memory — even outscored the full-size 120B teacher on LiveCodeBench (66.5 vs. 66.0), and a head-to-head comparison against QAT on a GPT-OSS 9B model showed QAH reaching a similar or better peak with a more stable training curve. The results suggest a smaller, cheaper 4-bit model can be more accurate than its own full-precision source, inverting the usual size-versus-accuracy tradeoff for teams deploying compressed models in production.

> 💡 Teams serving structurally compressed, quantized models should recognize that the common QAD approach caps accuracy by distilling from an already-degraded recovered checkpoint, and that switching to QAH — distilling straight from the original full-precision model — can meaningfully raise accuracy without added serving infrastructure cost.

### [Wire It, Run It, Deploy It: AI Workflows in Gradio](https://huggingface.co/blog/gradio-workflow-guide)

_Hugging Face_

This Hugging Face post introduces Gradio's new `gr.Workflow` feature, which turns a pipeline of AI models and functions into a visual graph instead of hand-wired Python code. Users connect typed nodes — references (inputs), operators (processing steps), and subjects (outputs) — on a drag-and-drop canvas where every node is runnable and every intermediate result is visible; the same graph automatically becomes a REST API and deploys to Hugging Face Spaces with one command. Example workflows include a single-node image editor built on Qwen-Image-Edit, a media studio that chains FLUX image generation into background removal, text-to-speech, and an LLM-generated title (with each output exposed as its own endpoint like /sticker, /voiceover, /episode_title), a fan-out pattern that generates multiple parallel image variants from one prompt, a dataset-profiling app that fans a single Hugging Face dataset ID out to four parallel analysis nodes, and a GPU-backed node using the `@spaces.GPU` decorator so ZeroGPU allocates a GPU only when that node runs. An operator can be a custom Python function, a model via Hugging Face Inference Providers, another Gradio Space, or a row from a Hub dataset, and any completed workflow can be called from Python via `gradio_client` or plain curl. Getting started takes just a few lines — `gr.Workflow(bind=[your_function]).launch()` — and every example is a live, duplicable Hugging Face Space rather than a static code sample.

> 💡 The fact that every workflow node automatically becomes its own REST endpoint means a prototyped multi-model pipeline can be wired straight into internal services or production integrations without building a separate API gateway, meaningfully shortening deployment lead time.

### [Bringing gVisor sandboxes to distributed Ray clusters](https://cloud.google.com/blog/products/containers-kubernetes/gvisor-sandboxes-for-ray-clusters-on-gke/)

_Google Cloud_

Google Cloud, in partnership with Anyscale, introduced an experimental library that brings native gVisor-based sandboxing directly into distributed Ray clusters, aimed at RL post-training workflows. As agentic and reasoning models scale up, safely isolating dynamic rollouts, code generation, and multi-turn tool interactions had become a bottleneck for frameworks like veRL, NeMo-RL, SLIME, MILES, and SkyRL that already run on Ray. Rather than inventing a separate abstraction, Ray Sandboxing represents each sandbox as a Ray Actor so the existing Ray scheduler handles placement, CPU/memory reservation, lifecycle, and failure recovery; starting in Ray 2.58, the `ray.experimental.sandbox` API lets developers create sandboxes from OCI-compatible images and execute commands, manage files, and inspect or tear down state using familiar Ray calls. A lower-level `SandboxRuntime` API is also available for building custom sandbox pools inside an actor. gVisor was chosen because it implements much of the Linux syscall interface in userspace, adding an isolation boundary between untrusted, model-generated code and the host kernel, while remaining OCI-compatible, requiring no exposed Docker daemon, and offering sub-second startup with low per-sandbox memory overhead — properties suited to using sandboxes as fine-grained distributed resources. Google plans to extend support to other sandboxing runtimes like Agent Substrate or Kata Containers in future Ray releases. The feature is explicitly experimental, and interested teams are directed to the Ray documentation, a GKE user guide, and a GitHub issue for feedback.

> 💡 For teams running RL or agentic pipelines on GKE that must treat model-generated code and tool calls as untrusted, being able to manage gVisor sandboxes as first-class Ray Actors inside the existing scheduler and failure-recovery model — rather than bolting on separate isolation infrastructure — meaningfully cuts operational complexity.

### [Preparing OpenStack for the post-quantum era: A systematic approach to crypto-agility](https://www.redhat.com/en/blog/preparing-openstack-post-quantum-era-systematic-approach-crypto-agility)

_Red Hat_

Red Hat published the results of a systematic audit of post-quantum cryptography (PQC) vulnerabilities across the entire OpenStack ecosystem. The concern is 'Q-day' — the future moment when a cryptographically relevant quantum computer running Shor's algorithm breaks RSA, ECDSA, ECDH, and Ed25519, the very algorithms OpenStack relies on for token signing, key generation, TLS, and secret storage — which already creates present-day risk via 'harvest now, decrypt later' attacks on data encrypted today. An upstream PQC Migration Pop-up Team formed at the April 2026 PTG, combined with 27 downstream engineering teams analyzing over 90 repositories using a purpose-built scanner, documented 572 findings and 39 cross-cutting patterns across 23 teams, independently validated by a separate security review. Four systemic patterns emerged: Barbican's SimpleCrypto plugin only generates RSA and DSA keys; Keystone signs tokens with hardcoded ECDSA P-256 with no configuration option to switch algorithms; oslo.messaging's legacy SSL version map has no TLS 1.3 entry, blocking PQC hybrid key exchange for all interservice messaging; and cert-manager/Go-based operators default to RSA-2048 or allow protocol downgrades when no explicit minimum TLS version is set. Encouragingly, a meaningful share of findings resolve automatically once the platform upgrades to OpenSSL 3.5 (which natively ships ML-KEM/FIPS 203 and ML-DSA/FIPS 204) and pyca/cryptography 48.0/49.0, as long as application code doesn't itself restrict TLS protocol versions or cipher suites — meaning some fixes require no code changes at all, while the hardcoded cases require targeted engineering work.

> 💡 Organizations running OpenStack should prioritize by separating findings that resolve automatically with an OpenSSL 3.5 platform upgrade from those requiring direct application-code fixes because of hardcoded algorithm choices in components like Keystone and Barbican, and this post's four systemic patterns can serve directly as that triage checklist.
