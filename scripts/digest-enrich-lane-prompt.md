# Daily Digest 보강 — 워커 레인 프롬프트 (일괄 회수용)

`digest-enrich-prompt.md` 는 매일 도는 세션이 **저장소 안에서** 보강·생성·커밋까지 하는 프롬프트다.
이 파일은 다르다: 밀린 날짜를 **일괄 회수**할 때 `agyp` 워커에게 던지는 프롬프트로,
워커는 저장소를 건드리지 않고 **JSON 하나만** 내놓는다. 검증과 병합은 오케스트레이터가
`scripts/enrich-apply.mjs` 로 한다 — 워커에게 저장소 쓰기를 맡기지 않는 것이 요점이다.

쓰는 법 (`SPEC_IN`/`SPEC_OUT` 을 실제 경로로 치환해 통째로 넘긴다):

```bash
agyp "$(sed -e "s#SPEC_IN#$IN#" -e "s#SPEC_OUT#$OUT#" scripts/digest-enrich-lane-prompt.md)" \
  --model "Gemini 3.6 Flash (High)" > "$LOG" 2>&1
node scripts/enrich-apply.mjs --date <날짜> --from "$OUT"
```

---

데일리 테크 다이제스트 기사에 한국어/영어 요약과 인사이트를 채워라.

## 입력
`SPEC_IN` 경로의 JSON 배열. 각 원소: `{source, category, title, link, date, excerpt}`.

## 출력
`SPEC_OUT` 경로에 **JSON 배열만** 써라. 다른 텍스트·설명·코드펜스 금지.
입력과 **같은 순서, 같은 개수**로, 각 원소는 정확히 이 5개 키만 가진다:

```json
[
  {
    "link": "<입력의 link 를 글자 그대로 복사>",
    "summaryKo": "...",
    "summaryEn": "...",
    "insightKo": "...",
    "insightEn": "..."
  }
]
```

## 내용 규칙

- 독자는 **Cloud / DevOps 엔지니어**다. 마케팅 톤이 아니라 엔지니어 톤으로 쓴다.
- `summaryKo` / `summaryEn`: **3~7문장.** 길이는 목표가 아니라 상한이다.
  원문에서 확인한 사실이 3문장어치뿐이면 3문장에서 끝내라.
- **요약에는 그 기사에서 가장 구체적인 것이 반드시 들어가야 한다** — 고유명사, 수치,
  벤치마크 점수, 가격, 날짜, 등장 기업·인물. 이것들이 빠지고 일반론만 남으면 실패다.
- `insightKo` / `insightEn`: **정확히 1문장.** "이 소식이 클러스터 운영·비용·보안·배포·관측성에
  어떤 의미인지". 요약을 반복하지 말고 시사점을 써라. 인사이트는 해석이므로 원문에 없어도 되지만,
  원문에 없는 **사실**을 인사이트에 새로 넣지는 마라.
- `summaryKo`와 `summaryEn`은 같은 내용이어야 하지만 **번역투를 피하고** 각 언어로 자연스럽게 쓴다.

## 근거 규칙 — 가장 중요하다

- **`link` 의 원문을 반드시 열어라.** 발췌만 보고 쓰지 마라.
- **원문을 못 열었으면 `title` + `excerpt` 범위 안에서만 쓰고, 그 사실을 요약 끝에 한 문장으로 밝혀라.**
- **원문에서 확인되지 않은 수치·버전·제품명·기능명·인용은 절대 지어내지 마라.**
- 쓰고 나서 **문장마다 "이건 원문 어디에 있나"를 자문하라. 답할 수 없는 문장은 지워라.**
  짧아지는 것은 문제가 아니다. 지어낸 문장이 하나 들어가는 것이 문제다.
- `excerpt` 가 비어 있는 기사도 `title` 과 원문 기준으로 채워라 — 요약이 있어야 본문에 편입된다.

### 실제로 걸러낸 실패 (같은 실수를 하지 마라)

분량을 채우려고 그럴듯한 일반론을 지어내는 것이 이 작업에서 가장 흔한 실패다. 실측 사례:

- Gemini 3.7 Flash 기사에서 `hybrid reasoning`, `deployment scripts`, `bug fixes`,
  `large codebases` 를 능력으로 서술했는데 **원문에 그런 말이 없었다.** 정작 원문의 핵심인
  도입가 절반·2027-01-01 인상, FrontierCode 34.4%→43.6% 는 요약에 없었다.
- 멀티테넌시 기사에서 "fifty engineers manage hundreds of active changes" 라고 썼는데
  **원문에 그런 숫자가 없었다.** 원문에 있던 "2,000 Claude Code sessions across two weeks" 는 빠졌다.
- 애플 기사에서 **Alibaba·Qwen·Baidu·Reuters 를 전부 빠뜨리고** 일반적인 개발자 조언으로 채웠다.

세 경우 모두 문장은 매끄러웠고 기계 검증도 통과했다. 사람이 원문과 대조해서야 드러났다.

## 언어 규칙 (기계 검증된다)

- `summaryKo` / `insightKo` — **한글로 쓴다.** 기술 용어·제품명은 원어 그대로 둬도 된다.
- `summaryEn` / `insightEn` — **영어로만 쓴다. 한글·한자·가나가 한 글자라도 섞이면 실패다.**
  (실제 사고: 영어 요약에 `people每 week` 처럼 한자가 섞여 들어간 적이 있다.
  단, 원문 저자명 같은 고유명사를 괄호로 병기하는 것은 예외로 허용된다.)
- 기계 오역을 만들지 마라. 실제로 걸러낸 것들: `초고통량`·`초고전압`(→`초고처리량`),
  `1분기 관리형`(fully managed 가 깨진 것 → `완전 관리형`), `파브릭`→`패브릭`,
  `인베딩`→`임베딩`, `멀티 텐런트`→`멀티 테넌트`, `보트`→`봇`, `미업`→`미트업`.
- 네 필드 모두 비어 있으면 안 된다.

## 하지 말 것

- 저장소 파일을 수정하지 마라. `git` / `gh` / `npm` 명령을 쓰지 마라.
- 입력 JSON 의 `link` 를 고치지 마라 — 병합 키다. 한 글자라도 달라지면 그 기사는 버려진다.
- 출력 파일 외에 아무것도 만들지 마라.

## 마지막에

출력 파일을 다시 읽어 (1) 원소 개수가 입력과 같은지, (2) JSON 이 파싱되는지,
(3) `summaryEn`/`insightEn` 에 한글이 없는지 확인하고, 결과를 한 줄로 보고하라.
